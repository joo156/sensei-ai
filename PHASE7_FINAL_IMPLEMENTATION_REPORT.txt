3. DATABASE MIGRATIONS (011–014)
--------------------------------
011_document_security.sql — document/generation/review RLS ownership model:
  * GRANTs so the Data API can serve documents, chunks, embeddings,
    generations, generation_versions, reviews and history to `authenticated`
    (coarse layer; RLS below is the actual gate). `service_role` granted ALL
    for symmetry — never used in frontend code.
  * Staff (reviewer/admin, via `has_full_access`) read policies on documents,
    generations, chunks, embeddings, generation_versions, history.
  * Owner read policy on reviews (owners may read their workspace review
    trail; staff already have FOR ALL from the base schema).
  * All policies created inside pg_policies existence guards → idempotent.
  * 001 already covered owner CRUD on documents/generations/chunks/embeddings/
    versions and staff write on reviews; nothing existing is dropped/rewritten.

012_storage_security.sql — secure Supabase Storage:
  * Ensures the private `documents` bucket exists (public=false, 100 MB limit,
    no MIME restriction), layout `<workspaceId>/<documentId>/<fileName>`.
  * Drops the three lax 002 policies ("any authenticated user can
    upload/read/delete") and replaces them with ownership-aware ones:
      upload/update/delete  → workspace owner only
      download (select)     → workspace owner OR staff (has_full_access)
  * Adds `storage_workspace_id(text)` (safe uuid extraction from a path) and
    `get_document_signed_url(text, int DEFAULT 3600)` SECURITY DEFINER — files
    are only ever served via short-lived signed URLs, never public access.

013_realtime_and_notifications.sql — realtime + notification backend support:
  * Adds workspaces, documents, generations, reviews and notifications to the
    `supabase_realtime` publication (guarded by pg_publication_tables).
  * `create_notification(uuid, uuid, app_role[], text, text, text)` single
    write point (SECURITY DEFINER).
  * Triggers: notify_generation_created (AFTER INSERT ON generations),
    notify_review_finished (AFTER INSERT OR UPDATE ON reviews),
    notify_document_uploaded (AFTER INSERT ON documents) — all target the
    workspace owner via the `notifications` table.
  * Role-targeted read policy ("Staff can read role notifications") so
    reviewers/admins can receive broadcast notifications via the `roles`
    array. Existing "Users read their own notifications" policy (001) is
    untouched. No notification UI added — backend/service support only.

014_performance_indexes.sql — database optimization:
  * CREATE INDEX IF NOT EXISTS on reviews(workspace_id, created_at DESC),
    notifications(user_id, read), generations(created_by),
    documents(workspace_id, created_at DESC), history(workspace_id, created_at
    DESC), chats(workspace_id, created_at DESC). Fully idempotent, no DROP.

4. DB / SECURITY / RLS SUMMARY
------------------------------
  * RLS remains enabled on every ownership table (001 base policies) and on
    workspaces (009). The view predicate + RLS together enforce: student sees
    only owned rows, reviewer/admin sees all (has_full_access).
  * New in this phase: staff read path on child tables (011), owner read path
    on reviews (011), ownership-aware storage policies + signed URLs (012).
  * No table is readable by the anon role for these surfaces; nothing is
    served through public storage.
  * Role checks in the UI still go through `useAuth().can()` /
    `usePermissions()` / `<RoleGate>` — no inline role comparisons were added.

5. REALTIME / NOTIFICATIONS
---------------------------
  * Realtime is consumed only for workspace changes and only invalidates the
    workspace-bootstrap cache — no broad cache clears, no new polling.
  * Notifications are written by SECURITY DEFINER triggers (owner-targeted)
    and read through RLS; the frontend already lists them via
    NotificationCenter with a now user-scoped query key.
  * Deliberately no notification UI churn: the schema/policies/triggers land
    now so the backend (FastAPI/edge) and UI can adopt them later.

11. KNOWN LIMITATIONS
---------------------
  * The base schema (workspaces, documents, generations, profiles,
    user_roles, app_role) is still not fully captured as real migrations —
    001–007 are stubs; docs/DATABASE_SCHEMA.md is the reference. Worth
    folding into migrations eventually.
  * The `security_invoker = true` conversion of the workspace view is
    deliberately deferred (needs base-table grants + child-table RLS — Phase
    7.3 already covers child-table RLS, so this is now low-risk but still
    optional).
  * Notification triggers fire on INSERT/UPDATE regardless of who wrote the
    row; duplicate-ish notifications on repeated UPDATEs are possible
    (acceptable for the lightweight model).
  * The signed-URL helper returns the URL from Supabase storage admin; if the
    project has no storage credentials configured the call fails loudly —
    expected until storage is wired.
  * Realtime requires the Supabase project's realtime service to be enabled
    for the added tables (migration 013 only handles the publication).

16. DESIGN DECISIONS
--------------------
  * SECURITY DEFINER helpers (has_role/has_full_access/signed URL) kept, with
    explicit search_path; has_full_access(NULL) = true is intentional for
    trusted non-JWT contexts — do not change without auditing service_role /
    cron callers.
  * Policies created idempotently via pg_policies guards; functions via
    CREATE OR REPLACE; indexes via CREATE INDEX IF NOT EXISTS.
  * Realtime invalidation deliberately narrow (single query key) to avoid
    refetch storms.
  * Storage policies key off the first path segment (workspace uuid), so no
    new metadata column is needed to scope ownership.
