# PHASE 7.2 AUTO-REFRESH — STALE BOOTSTRAP DATA AFTER LOGIN (FIXED)

Status: COMPLETE — frontend-only fix. No RLS / SQL migration / Supabase
function changed. Verified with `npx tsc --noEmit` (0 errors), `npm run lint`
(0 errors; only pre-existing react-refresh warnings), `npm run build` (passes).

## Root cause

`WorkspaceProvider` cached its bootstrap query under a **global, non-user-scoped
key**:

```tsx
useServiceQuery(["workspace-bootstrap"], () => WorkspaceService.bootstrap(), ...)
```

The React Query cache lives for the whole SPA session (single `QueryClient` in
`src/router.tsx`). `WorkspaceProvider` stays mounted across auth changes
(login / logout / account switch without a full page reload). Because the query
key never changed, React Query kept serving the **previous account's** cached
`workspace_with_owner` rows immediately after login — no refetch was triggered
until the manual Refresh button (which just `invalidateQueries`). The backend
(RLS + `workspace_with_owner` view) was correct; the app was displaying stale
cache.

## Changes

### 1. `src/contexts/WorkspaceContext.tsx` — user-scoped query key

```tsx
const { user } = useAuth();
useServiceQuery(
  ["workspace-bootstrap", user?.id ?? null],
  () => WorkspaceService.bootstrap(),
  { refetchOnWindowFocus: true },
);
```

Why:
- React Query derives cache entries from the full key, so the bootstrap data is
  now partitioned **per authenticated user**. After an account switch the new
  user's key has no cache entry, so the query is forced into a fresh fetch and
  the previous user's list can never be shown (requirement 4).
- A key change flips the query to `isPending`, so `WorkspaceProvider` renders
  `LoadingState` and the inner `WorkspaceStore` **unmounts and remounts** with
  the fresh server list — the old `activeId`, `workspaces` list and per-workspace
  `store` are discarded, fully clearing the previous account's workspace state
  (requirement 5).
- `refreshWorkspaces()` / `addWorkspace()` still call
  `invalidateQueries({ queryKey: ["workspace-bootstrap"] })`, which matches all
  user variants by prefix — existing behaviour preserved.
- While signed out the key is `["workspace-bootstrap", null]`; `user?.id` is
  available because `WorkspaceProvider` renders inside `AuthProvider`
  (`src/routes/__root.tsx`), and no import cycle exists.

### 2. `src/contexts/AuthContext.tsx` — purge other users' cache on auth change

Added `useQueryClient()` and a helper:

```tsx
const clearOtherUsersWorkspaces = useCallback((currentUserId: string | null) => {
  queryClient.removeQueries({
    queryKey: ["workspace-bootstrap"],
    predicate: (query) => !query.queryKey.some((part) => part === currentUserId),
  });
}, [queryClient]);
```

Called at every session transition point:
- `login` → `clearOtherUsersWorkspaces(next.user.id)`
- `logout` → `clearOtherUsersWorkspaces(null)`
- `refreshSession` → `clearOtherUsersWorkspaces(next?.user.id ?? null)`

The predicate keeps only the **current** user's entry, so switching identity
purgers the previous account's cached list (requirement 5) without removing the
current user's already-fresh entry — which is why there is exactly one fetch per
login, no duplicate requests and no refetch loops (requirement 8).

## Requirement-by-requirement

1. Auto-invalidate + refetch on login — the login flow changes the auth state;
   the user-scoped key yields a fresh fetch automatically. No manual Refresh.
2. No manual Refresh needed — satisfied by the key change (fetches on mount with
   the new user key).
3. WorkspaceProvider always receives a fresh list after auth changes — yes: new
   key → new fetch → fresh `seedWorkspaces`.
4. Never reuses the previous user's bootstrap data — cache partitioned by user
   id, plus the purge helper.
5. Clears old cache on user change — `removeQueries` purge on login/logout/
   refreshSession; `WorkspaceStore` remounts on key change.
6. Preserves existing functionality — no other files touched; `invalidateQueries`
   prefix still works; RLS/migrations untouched.
7. No RLS / SQL / Supabase function changes — frontend only.
8. No duplicate requests / infinite loops — current user's cache entry is kept;
   the purge runs once per identity change; the new-key query fetches exactly once.
9. Consistent with architecture — cache lifecycle lives in React Query
   (`useServiceQuery`), auth owns session transitions, workspace data ownership
   stays in `WorkspaceProvider`/`WorkspaceService`.
