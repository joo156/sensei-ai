PHASE 7.2 — WORKSPACE VISIBILITY + REFRESH: IMPLEMENTATION RESULT
=================================================================

Date: 2026-08-06
Status: Implemented, type-checked, linted, built.

1. OVERVIEW
-----------
Completed Phase 7.2 on top of Phase 7.1 (workspace ownership view + owner
metadata). Scope:

  * Fixed the stale-workspace bug (a workspace deleted in Supabase kept
    showing in the UI until another workspace was created).
  * Workspace visibility is now enforced server-side: students see only
    workspaces they own, reviewers see their own plus all student
    workspaces, admins see everything.
  * Query-cache sync after create/refresh mutations.
  * Richer Workspace Switcher (owner info, review status, counts).
  * A manual "refresh" control in the switcher.

Phase 7.3 was NOT started (no document/child-table RLS, no storage buckets,
no realtime, no large React Query refactor).

2. FILES MODIFIED (this phase)
------------------------------
  src/contexts/WorkspaceContext.tsx
      - Server list is now authoritative: a sync effect propagates
        `data.workspaces` into WorkspaceStore state whenever the bootstrap
        query refreshes (fixes the stale-workspace bug).
      - Hydration no longer resurrects deleted workspaces: persisted
        workspaces are never written over the server list; only the active
        id and per-workspace draft data are restored, scoped to workspaces
        that still exist server-side.
      - `useServiceQuery` for the bootstrap now sets
        `refetchOnWindowFocus: true`.
      - New `refreshWorkspaces()` on the context: invalidates
        `["workspace-bootstrap"]`.
      - `addWorkspace()` now also invalidates `["workspace-bootstrap"]` so
        the cache re-syncs after a create.

  src/router.tsx
      - The single `QueryClient` created by `getRouter()` now sets
        `refetchOnWindowFocus: true` (default for the whole app; previously
        the option was only needed at the provider query, now both agree).
        `src/routes/__root.tsx` consumes this same client (verified), so it
        needed no change.

  src/components/app/AppShell.tsx
      - WorkspaceSwitcher redesigned: stacked row layout (workspace name →
        owner name/email → ReviewBadge + pending/generations/docs counts),
        owner/counts dimmed for the student role.
      - Added a refresh (RefreshCw) action in the switcher header wired to
        `refreshWorkspaces()`.

  src/api/workspace.api.ts
      - No functional change this phase. The prior plan proposed an
        explicit-column `dbProps` select to "avoid a security_definer_view
        error (PGRST301)". Research (PostgREST error docs) shows PGRST301 is
        a JWT-verification error (401), NOT a view-columns error, and `"*"`
        on the view already works in the live project, so the plain
        `.select("*")` path is kept. The real visibility fix is the view
        WHERE clause in migration 009.

3. DATABASE CHANGES
-------------------
  supabase/migrations/008_workspace_ownership.sql
      - Already written and applied to the live project (Phase 7.1).
        Creates `workspace_with_owner` view + supporting indexes + GRANTs.

  supabase/migrations/009_workspace_visibility.sql  (NEW — APPLY TO SUPABASE)
      - `app_role` enum + `user_roles` table (guarded/IF NOT EXISTS; the
        base schema lives outside the migration chain, these are the only
        hard Phase 7.2 prereqs).
      - `has_role(user_id, app_role)` SECURITY DEFINER helper (documented in
        docs/SUPABASE_INTEGRATION.md).
      - `has_full_access(uid)` = admin OR reviewer; NULL uid (service_role /
        SQL editor / cron — no JWT) counts as full access so trusted
        contexts keep reading. The anon role never reaches it (no GRANT on
        the view).
      - RLS enabled on `workspaces` with policies:
          workspace_owner_access  FOR ALL  USING/WITH CHECK owner_id = auth.uid()
          workspace_staff_read    FOR SELECT USING has_full_access(auth.uid())
          workspace_staff_write   FOR UPDATE USING has_full_access(auth.uid())
        (INSERT = owner only via WITH CHECK; matches the documented §5
         contract and PHASE7_ARCHITECTURE_REVIEW "UPDATE/DELETE owner/admin".)
      - Indexes: workspaces(owner_id), user_roles(user_id).
      - `workspace_with_owner` re-created (CREATE OR REPLACE) with a WHERE
        predicate: `has_full_access(auth.uid()) OR owner_id = auth.uid()`.
      - GRANTs re-issued idempotently.

  DESIGN NOTE on the view + RLS:
      The view is deliberately kept SECURITY-DEFINER (so the owner-info
      joins to profiles/auth.users keep working with only the view-level
      GRANT and no new base-table/auth.users grants), and every returned row
      is gated by the same predicate the RLS policies use. The Supabase
      database linter flags security-definer views (lint 0010); that warning
      is expected — the view self-filters, so it is not a leak. Converting
      the view to `security_invoker = true` (the modern Supabase
      recommendation) was evaluated but deferred: it would require SELECT
      grants on documents/generations/profiles/auth.users plus RLS policies
      on child tables — that is Phase 7.3 scope.

  ACTION REQUIRED: run 009_workspace_visibility.sql against the live
  Supabase project (same as 008). Without it the old behaviour (all
  workspaces visible to every authenticated user) remains.

4. BUGS FIXED
-------------
  Stale workspace list (deleted-in-Supabase workspace still shown):
     1. WorkspaceProvider loads `["workspace-bootstrap"]` via useServiceQuery.
     2. WorkspaceStore copies `data.workspaces` into local state — but the
        query result was only read at mount, and the hydration effect then
        OVERWROTE the list from localStorage (resurrecting deleted ones).
     3. Even when React Query refetched (window focus), nothing propagated
        `data.workspaces` back into WorkspaceStore state.
     4. No mutation invalidated the bootstrap query.
     Fix: hydration no longer writes the workspace list; a sync effect
     propagates server data on every refresh; the query refetches on window
     focus; create + manual refresh invalidate the cache; RLS/view WHERE
     prevents deleted/invisible workspaces from being returned at all.

6. UPDATE — IDEMPOTENT MIGRATION 009 (added after initial implementation)
-------------------------------------------------------------------------
  Requested change: make the migration idempotent instead of relying on
  function replacement — detect an existing function and only create it if
  missing (or explicitly drop-and-recreate in a controlled way). Because 009
  doubles as a one-shot migration-history entry AND a re-runnable SQL-editor
  script, the detect-and-create approach was chosen over drop-and-recreate
  (no destructive step, nothing silently overwritten).

  What changed in supabase/migrations/009_workspace_visibility.sql:
    - `has_role(uuid, public.app_role)` is now created inside a DO block that
      checks `to_regprocedure('public.has_role(uuid, public.app_role)')` and
      only CREATE FUNCTIONs when it returns NULL. The definition is identical
      to before (SECURITY DEFINER, STABLE, set search_path, same body).
    - `has_full_access(uuid)` uses the same detect-and-create pattern with
      `to_regprocedure('public.has_full_access(uuid)')`.
    - The two CREATE OR REPLACE FUNCTION statements were replaced by these
      guarded DO blocks; NOTHING is DROPped and an existing function keeps
      its original definition if already present.
    - Header comment updated to document the idempotency contract per object:
        * app_role enum        -> pg_type existence check (DO block)
        * user_roles table     -> CREATE TABLE IF NOT EXISTS
        * has_role / has_full_access -> to_regprocedure check (DO blocks)
        * RLS policies         -> pg_policies existence check (DO block)
        * indexes              -> CREATE INDEX IF NOT EXISTS
        * workspace_with_owner view -> CREATE OR REPLACE VIEW (safe,
          non-destructive, re-applies the visibility WHERE clause)
        * GRANTs               -> re-issued, inherently idempotent
    - Why not CREATE OR REPLACE for the functions: OR REPLACE silently
      overwrites an existing same-signature body and cannot change the return
      type; for a migration history the guard-or-create pattern is explicit
      and leaves prior state untouched. Why not DROP FUNCTION ... CASCADE:
      destructive on dependent objects (policies, view) and would require
      re-creating everything downstream.

  Functional behaviour is unchanged: same function signatures, same
  definitions, same grants, same policies, same view predicate. Verification
  for the codebase (tsc/lint/build) is unaffected by this SQL-only change.
