## 1. OLD `has_role()` (001_initial_schema.sql, already live) vs NEW `has_role()` (009)

OLD (001, line 450 — `create or replace`, so it exists in the live DB):
```sql
create or replace function public.has_role(
    _user_id uuid,
    _role app_role
)
returns boolean
language sql
stable
security definer
set search_path = public
as $$
    select exists (
        select 1
        from public.user_roles
        where user_id = _user_id
          and role = _role
    );
$$;
```

NEW (009, line 70-87 — created ONLY if missing):
```sql
IF to_regprocedure('public.has_role(uuid, public.app_role)') IS NULL THEN
    CREATE FUNCTION public.has_role(user_id uuid, required public.app_role)
    RETURNS boolean
    LANGUAGE sql
    STABLE
    SECURITY DEFINER
    SET search_path = public
    AS $fn$
      SELECT EXISTS (
        SELECT 1 FROM public.user_roles ur
        WHERE ur.user_id = has_role.user_id
          AND ur.role   = has_role.required
      );
    $fn$;
END IF;
```

Verdict: the two bodies are **functionally identical** (both are
`EXISTS(SELECT 1 FROM public.user_roles WHERE user_id = X AND role = Y)`).
Because 001 already created `has_role`, 009's `to_regprocedure` guard resolves
to a non-NULL OID and **009 silently skips creating its own version**. The OLD
001 `has_role` remains the live definition. Function-overload resolution binds
`public.has_role(...)` everywhere to that OLD function.

## 6. SINGLE ROOT CAUSE

**`has_full_access()` is calling the OLD `has_role()` from 001 — 009's
`to_regprocedure` guard skips installing its own `has_role`, so Phase 7.2's
visibility gate is bound to the pre-existing OLD function and the live
`user_roles` data it reads. In the live DB that OLD function + data resolves
the "student" account as staff (`has_role(auth.uid(),'reviewer')` or
`'admin'` = TRUE), so `has_full_access(auth.uid())` = TRUE, the view's
`WHERE public.has_full_access((select auth.uid()))` passes for EVERY row, and
the student sees every workspace.**

Mechanism, precisely:
1. 001 (base schema, already applied) defined `has_role` via `create or replace`.
2. 009's detect-and-create guard (`to_regprocedure('public.has_role(uuid, public.app_role)')`)
   finds it and does nothing — the NEW `has_role` never exists. (And, per §1,
   even if it did, its body equals the old one, so 009 alone cannot change the
   role result.)
3. 009's `has_full_access` (which WAS created) calls that OLD `has_role`.
4. For the student uid, the OLD `has_role` returns TRUE for `'reviewer'`/`'admin'`
   (i.e. the live `user_roles` row set for that account includes a staff role),
   so `has_full_access(student)` = TRUE.
5. Every row of `workspace_with_owner` therefore satisfies
   `has_full_access((select auth.uid()))` and the whole table is returned.

The fix must make the live `has_role` (and `has_full_access`) be the exact,
intended definitions REGARDLESS of what already exists — the current guard
cannot, because it preserves the old function and old data verdict.

## 7. SAFEST MIGRATION 010 (replace only what is necessary)

CREATED on disk as `supabase/migrations/010_workspace_visibility_hard_fix.sql`

Goal: force the intended `has_role`/`has_full_access` to be the live ones using
`CREATE OR REPLACE` (non-destructive — no DROP, no dependency breakage; the
view and policies keep their references), then re-assert the view + grants.
Does NOT touch tables, enums, triggers, or any object created by 001/008/009.

```sql
-- 010_workspace_visibility_hard_fix.sql
-- Phase 7.2 root-cause fix: 009's to_regprocedure guard skipped replacing the
-- OLD has_role from 001, so has_full_access was bound to the old function and
-- live user_roles data. CREATE OR REPLACE is non-destructive: it swaps the
-- function body in place, keeps the same OID, and does not break the view or
-- policies that reference these functions. Re-runnable / idempotent.

CREATE OR REPLACE FUNCTION public.has_role(user_id uuid, required public.app_role)
RETURNS boolean
LANGUAGE sql
STABLE
SECURITY DEFINER
SET search_path = public
AS $fn$
  SELECT EXISTS (
    SELECT 1 FROM public.user_roles ur
    WHERE ur.user_id = has_role.user_id
      AND ur.role   = has_role.required
  );
$fn$;

CREATE OR REPLACE FUNCTION public.has_full_access(uid uuid)
RETURNS boolean
LANGUAGE sql
STABLE
AS $fn$
  SELECT uid IS NULL
      OR public.has_role(uid, 'admin')
      OR public.has_role(uid, 'reviewer');
$fn$;

GRANT EXECUTE ON FUNCTION public.has_role(uuid, public.app_role) TO authenticated;
GRANT EXECUTE ON FUNCTION public.has_full_access(uuid) TO authenticated;

-- Re-assert the gate (same shape as 009; CREATE OR REPLACE keeps it idempotent).
CREATE OR REPLACE VIEW public.workspace_with_owner AS
SELECT
    w.id, w.owner_id, w.name, w.subject, w.description, w.accent,
    w.created_at, w.updated_at,
    p.full_name AS owner_name,
    au.email    AS owner_email,
    (SELECT count(*) FROM public.documents d WHERE d.workspace_id = w.id) AS document_count,
    (SELECT count(*) FROM public.generations g WHERE g.workspace_id = w.id) AS generation_count,
    (SELECT count(*) FROM public.generations g
        WHERE g.workspace_id = w.id AND g.review_status = 'pending') AS pending_review_count,
    COALESCE((
        SELECT g.review_status
        FROM public.generations g
        WHERE g.workspace_id = w.id
        ORDER BY g.created_at DESC, g.id DESC
        LIMIT 1
    ), 'pending') AS review_status
FROM public.workspaces w
LEFT JOIN public.profiles p ON p.id = w.owner_id
LEFT JOIN auth.users   au ON au.id = w.owner_id
WHERE public.has_full_access((select auth.uid()))
   OR w.owner_id = (select auth.uid());

COMMENT ON VIEW public.workspace_with_owner IS
    'Workspaces joined with owner identity and review summary, filtered to the caller''s visibility (Phase 7.1 + 7.2).';

GRANT SELECT ON public.workspace_with_owner TO authenticated;
GRANT SELECT ON public.workspace_with_owner TO service_role;
```

- It ONLY redefines the two helpers + re-asserts the view and grants. It does
  not drop/recreate tables, the enum, triggers, or 001/008/009 objects.
- It is idempotent and safe to run in the SQL editor repeatedly.
