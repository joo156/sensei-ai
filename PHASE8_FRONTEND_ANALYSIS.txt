1. EXECUTIVE SUMMARY
===============================================================================
Sensei-AI is a large, well-structured, mock-first prototype of a "production
quality" TanStack Start (SSR) grounded-AI study app. The engineering hygiene
is genuinely high: a clean service/api layering rule, zero TODO/FIXME markers,
strict TypeScript that passes, near-uniform AsyncState loading/error/empty
primitives, role-gating, and a thoughtfully documented contract surface
(docs/BACKEND_CONTRACT.md, docs/FASTAPI_INTEGRATION.md, src/types/api/*,
src/api/paths.ts).

The critical finding is that the frontend is NOT actually wired end-to-end to
the Phase 8 FastAPI backend. In its default, most-complete mode, the app runs
entirely from src/mock. When VITE_ENABLE_MOCK=false is set against a live
backend, the app becomes a broken hybrid:

  * Authentication, workspaces, documents (list/upload/create/delete) go
    through SUPABASE (src/lib/supabase.ts transpiled at env-time), while
    generation/chat/review/search/parse/chunk/embed/notes call the FASTAPI
    backend through src/api/http.ts. The two backends are independent and
    share no identity or data, so real mode cannot function as a coherent
    product.
  * The FastAPI backend's own auth scaffold (POST /auth/*, M1) is never called
    by the frontend; the frontend sends a SUPABASE Bearer token, which the
    backend's get_current_user (backend/deps.py) rejects with 401. The two
    auth systems are mutually incompatible until the backend's Supabase-JWT
    milestone lands.
  * Several backend milestones have NO frontend consumer: review workflow
    (M7) is implemented entirely in WorkspaceContext/setReview (local state),
    export (M8) has no frontend module at all (only toast() stubs), and
    history/analytics/models/catalogue/agents/pipeline/notifications point at
    endpoints the backend does not implement.

The right way to read this repo is: a "frontend-ready" prototype whose
service/API layer is designed to accept either a mock or a real backend, but
whose real-mode wiring is currently split-brain and unintegrated with the
Phase 8 backend. It is not production-ready for live-backend use; it is an
excellent high-fidelity mock / demo app with a clear path toward integration.

2. FOLDER ARCHITECTURE REVIEW
===============================================================================
Layer model (matches docs/FRONTEND_ARCHITECTURE.md and AGENTS.md rules):
  component -> hook/context -> Service -> *.api.ts -> (mock | http / supabase)

folder/review:
- src/routes/        File-based TanStack router pages. 13 feature routes +
                     __root, index (landing), sitemap. All import services,
                     never src/api or src/mock directly. GOOD.
- src/components/
    ui/              shadcn Radix primitives (sidebar, dialog, tabs, ...).
                     Standard, generated, thin.
    app/             Feature components (AppShell, AsyncState, InteractiveQuiz,
                     FlashcardDeck, QuestionCard, badges, ModelSelector,
                     GlobalSearch, Pipeline, ...).
- src/contexts/       AuthContext, WorkspaceContext, NotificationContext.
                     State ownership of user/workspace/notify.
- src/hooks/          useServiceQuery (Result-bridge to TanStack Query),
                     usePermissions (DEAD - see §11), use-mobile.
- src/services/       15 service singletons + ai/AIProvider abstraction.
                     The intended single swap seam. Well respected by routes.
- src/api/            paths.ts (path registry) + http.ts client + domain api
                     modules. Historical issue: auth/workspace/document
                     real-mode uses SUPABASE, not these FastAPI paths.
- src/types/          domain.ts (render shapes), api/*.contracts.ts (API
                     contracts), database.types.ts (Supabase snake_case schema).
- src/mock/           4 seed modules that back all api functions in mock mode.
- src/lib/            result.ts envelope, supabase.ts singleton, logger,
                     errorReporter, workspace helpers.
- src/config/env.ts    Vite env reading (see §3 footgun).
- src/constants/       roles/permissions/storage keys + generation kinds.
- src/start.ts/server.ts  TanStack Start server entry with CSRF + error
                     middlewares; sitemap route.

Assessment: architecture is arguably the strongest part of the repo. The
separation of "service seam" is real and consistent. The dominant weakness is
that the api layer has drifted to TWO backends (Supabase + FastAPI) without a
clear contract, which the service seam now hides rather than resolves.

3. API LAYER REVIEW  (src/api/*)
===============================================================================
3.1 paths.ts                     — single, documented path registry. GOOD.
3.2 http.ts                      — the ONLY network client. Bearer header is a
        single module-level `accessToken`; unwraps `{data}` envelopes; error
        shaping to HttpError with `.body` = {code,message,details}. 90s timeout
        (recently reworked, uncommitted). GOOD. Weaknesses:
          * No automatic 401 -> refresh/retry; a 401 surfaces as an error.
          * No retry on transient network failures.
          * "Content-Type": application/json set even for bodies that are
            already strings; benign.
3.3 auth.api.ts      — SUPABASE-based (signInWithPassword, getUser, refresh,
        profiles/user_roles merge). The FastAPI /auth/* endpoints in
        backend/auth are NEVER invoked. RED FLAG (see §5).
3.4 workspace.api.ts — REAL-mode uses Supabase (workspace_with_owner view,
        workspaces table); the FastAPI /workspaces/* router is unused. Also
        imports mock seeds (studio-data, users, workspace-data) for mock mode.
3.5 document.api.ts  — HYBRID. uploadDocument/createDocument/getDocuments/
        getDocumentsForWorkspaces/deleteDocument -> SUPABASE (documents table +
        storage bucket). parse/chunk/embed/chunks/notes -> http (FastAPI
        /documents/{id}/...). This is split-brain storage for the same entity.
3.6 search.api.ts    — http -> GET /search (FastAPI M4). GOOD parity of
        query params (q, workspace_id, limit, kinds).
3.7 generation.api.ts– http -> FastAPI /generate/*. PAYLOAD SHAPE MISMATCHES
        (see §4.5). Revision response adds `weakTopics`; study-plan response
        adds `days` — none present in the contract types.
3.8 chat.api.ts    — http -> FastAPI. getChats returns UNTYPED http.get (no
        generic). getChatsResponse is not imported/typed.
3.9 review.api.ts   — http -> FastAPI /review/*. Dead: no UI calls these.
3.10 history.api.ts / analytics.api.ts / model.api.ts / catalogue.api.ts —
        http -> (paths.history,/analytics,/models,/agents,/pipeline,/notifications,
        /catalogue). For EACH of these the backend main.py mounts NO such
        router (see §6). So in real-mode each of these 404s.
3.11 Envelope: client handles {data:T} or bare T; backend returns bare T for
        success. OK. Errors: contract {error:{...}} mapped to HttpError.body.
        NonJSON error bodies fall back to status only. OK.
3.12 conflict: `isMockMode()` returns `env.ENABLE_MOCK || env.API_BASE_URL
        === "/api"`. With env default left as "/api" (i.e., no VITE_API_BASE_URL
        set), the app silently stays in mock mode even if VITE_ENABLE_MOCK=false.
        A footgun that can hide an unintegrated build.
3.13 duplicated `toError(...)` in 4 api modules (document, workspace, auth) +
        http.HttpError: two competing error shapes. (list in §11).

4. ROUTING REVIEW
===============================================================================
- Protocol: TanStack Router, file-based, SSR via TanStack Start. routeTree.gen
  is in sync with files. GOOD.
- Against protected routes: protection is composed per-route through
  <RoleGate> + createFileRoute component. AppShell does NOT gate; it renders.
  There is NO global/route "if not authed -> redirect to /login" guard in
  __root.tsx. A stale client-side route bypass is possible only if a page
  is not wrapped; today every app page is wrapped so behavior is correct,
  but the pattern is not enforced (defense in depth missing).
- homeForRole() (constants) routes student->/home, reviewer->/review,
  admin->/admin. Consistent.
- sitemap[.]xml BASE_URL is "" (empty) so emitted <loc> are relative/invalid;
  also omits /workspace,/settings,/studio,/admin,/chat.
- 404 (NotFoundComponent) + error boundary (ErrorComponent) in __root.tsx are
  solid; error-reporting to BackendErrorReporter wired.

6. STATE MANAGEMENT REVIEW
===============================================================================
- TanStack Query (ReactingQuery) is present and used for READ paths through
  useQuery + unraw(), user/(workspace-bootstrap, analytics, catalogue, agents,
  notifications, plus useQuery for other apis).
- Only ONE useMutation in the whole app (NotificationCenter markAllRead).
  Everything else (generation, chat, review) uses imperative async-await
  + local mutable context state. Query cache invalidation is scoped to
  workspace-bootstrap + notifications.
- WorkspaceContext owns all writes: setReview/addDoc/updateDoc/addChat/
  addHistory etc. — purely in-memory + localStorage (workspaceState key). It
  does NOT persist to any backend. In "real mode" this means review decisions,
  chat, history, notes, approvals NEVER leave the browser.
- localStorage PersistShape restores per-workspace draft state keyed by
  conflict-safe storage keys. Server list is authoritative. Reasonable, but it
  is explicitly NOT a backend persistence story.
- Result<T> envelope (lib/result.ts) -> refund for EVERY service, Services
  "never throw". Good, uniform.

9. TYPESCRIPT CONTRACT AUDIT (frontend contracts vs backend Pydantic)

Contract files / Pydantic end match for the fields that exist. Notable mismatches:

9.1 Review / audit

  - backend returns OutputStatus.value = "pending"/"edited"/"approved"/"rejected"
    (lowercase). Contract ReviewResponse.status is typed ReviewState (title
    case) so "approved" is not assignable to "Approved", and there is no TS
    member for the backend's "edited" value. MISMATCH. (Note: the UI concept
    "Needs Edit" maps to backend status "edited", not "Needs Edit".)
  - WsAuditEntry.action (domain) = "Approved"/"Rejected"/... (title).
    Backend returns ReviewAction.value "approve"/"edit"/"reject"/"comment".
    MISMATCH (values differ in case and wording).
  - review.action BACKEND BUG: backend action_map map uses ReviewAction.NEEDS_EDIT
    and ReviewAction.FLAG members that DO NOT EXIST on ReviewAction enum
    (src/validation/review_schema.py has only approve/edit/reject/comment) —
    so review needs-edit and flag endpoints will 500. Any frontend integration
    of those two actions will be blocked until backend fixes the enum.

9.7 Search

15. FINAL VERDICT
===============================================================================
The Sensei-AI frontend is an impressively architected, aesthetically-polished,
strongly-typed prototype that is fully functional in its default mock mode.
As a real product integrated against the Phase 8 backend with production
habits (tokens, persistence, export, review-gate, retries,
testing), it is NOT production-ready and is NOT currently wired to the backend.

The single most important finding is that the frontend's real-mode is a
split-backend hybrid: identity + workspaces + document storage live in Supabase,
while generation/chat/review/search/pipeline read from a separate FastAPI build
whose SQLite/Chroma store is empty and whose document store `ingestion.db`
knows nothing about supabase-created ids. No real-mode end-to-end flow is
programmed today; uploading a file in real mode stores it in Supabase and then
fails to parse in FastAPI; logging in issues a valid session but the backend
rejects the bearer token because the two auth systems are different.

Until the team picks exactly ONE identity+storage stratum and rewires the
service/API layer to it (Option (a) or (b) in R1), flips VITE_ENABLE_MOCK=false
as a genuine integration gate, adds the missing review->export persistence,
fixes the contract-type mismatches, and adds a real test suite, the project
belongs in the "high-fidelity demo / Phase-8 frontend-ready" category rather
than "production". If integration proceeds, prioritize R1-R5; the remaining
work is well-scoped and the codebase is clean enough to absorb it.
