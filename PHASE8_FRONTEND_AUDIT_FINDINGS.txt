TOP-LEVEL VERDICT
-------------------------------------------------------------------------------
Sensei-AI is an excellently-architected, strongly-typed, mock-first prototype.
It runs fully in its default mock mode, but it is NOT wired end-to-end to the
Phase 8 FastAPI backend and is NOT production-ready for live-backend use.

===============================================================================
2. HEADLINE FINDING — THE FRONTEND IS NOT ACTUALLY INTEGRATED
===============================================================================
The most important result of the audit is that the Phase 8 backend is largely
NOT consumed by the frontend. The frontend's "real mode" is a split-backend
hybrid that cannot function as a coherent product:

  * Authentication, workspaces, and document list/upload/create/delete go
    through SUPABASE (src/lib/supabase.ts + auth/workspace/document api).
  * Generation, chat, review, search, parse/chunk/embed/notes go through the
    FASTAPI backend via src/api/http.ts.
  * The two backends store identity and data in separate systems with no link,
    so a single user sees empty / failing data in real mode.

===============================================================================
3. KEY FINDING — AUTH SYSTEMS ARE MUTUALLY INCOMPATIBLE
===============================================================================
  * Frontend authenticates with SUPABASE and sends a SUPABASE Bearer token.
  * Backend deps.get_current_user (backend/deps.py) only recognises its own M1
    password-scaffold tokens (looked up in local auth store). It will REJECT a
    Supabase token with 401.
  * The backend /auth/* endpoints (M1) are NEVER called by the frontend.
  * Resolving this is either:
      (a) make the backend accept the Supabase JWT (backend Supabase milestone),
      or (b) make the frontend log in via FastAPI /auth/* and store that token.
  => Currently impossible to have a working authenticated session against the
     backend. Blocking item number one.

===============================================================================
4. BACKEND MILESTONES WITH NO FRONTEND CONSUMER
===============================================================================
  M7 Review   : The review page (src/routes/review.tsx) drives state through

                or component calls ReviewService approve/reject/needs-edit/

  M8 Export   : There is NO ExportService, no export.api module, no export

  Models      : model.api targets /models — backend has no such router.
  Catalogue   : /agents, /pipeline/*, /notifications/*, /catalogue — backend

===============================================================================
5. SPLIT-BRAIN DOCUMENT STORAGE (Single uploads cannot complete)
===============================================================================
  * document.api.uploadDocument / createDocument / getDocuments / deleteDocument
    use SUPABASE (documents table + documents storage bucket).
  * But parse / chunk / embed / getChunks / saveDocumentNotes call FASTAPI
    (/documents/{id}/...).
  * In real mode: you upload a file -> stored in Supabase, but the FastAPI SQLite
    (ingestion.db) knows nothing of that id, so POST /documents/{id}/parse 404s.
  * So the upload pipeline breaks after "store" in real mode: no parsing,
    no chunking, no embedding, no retrieval index ever built.
  * search / grounded generation rely on the (empty) FastAPI Chroma index, so
    they return empty results.

===============================================================================
6. ENV / MOCK FOOTGUN
================================================================================
  * isMockMode() = env.ENABLE_MOCK || env.API_BASE_URL === "/api".
  * If VITE_API_BASE_URL is left at its default "/api", the app silently stays
    in mock mode EVEN IF VITE_ENABLE_MOCK=false. This hides unintegrated builds.
  * Current .env.local is already set to VITE_ENABLE_MOCK=false +
    VITE_API_BASE_URL=http://localhost:8000 + a real Supabase URL/anon key, which
    is exactly the broken hybrid configuration (see findings 4/5).

=======================================================================================
7. TYPESCRIPT CONTRACT MISMATCHES (frontend types vs backend Pydantic)
=======================================================================================
  7.1 Review status / action (real misalignment):
       - TS domain.ReviewState = "Pending" | "Approved" | "Needs Edit" | "Rejected"
       - Backend returns OutputStatus.value = "pending" | "edited" | "approved" | "rejected"
         => "approved" is not assignable to "Approved"; there is no TS member for
             backend "edited" (the concept "Needs Edit").
       - TS WsAuditEntry.action = "Approved"/"Rejected"/... vs backend
             ReviewAction.value "approve"/"edit"/"reject"/"comment". MISMATCH.
  7.2 Study plan response: backend returns {summary, sections, days}, contract
       GenerateStudyPlanResponse only declares {summary, sections[]}. Frontend
       re-adds `&{days: StudyPlanDay[]}` via inline intersection in
       generation.api (stopgap). Contract file is incomplete.
  7.3 Revision response: backend returns { summary, sections, weakTopics },
       contract GenerateRevisionSheetResponse omits weakTopics (same pattern).
  7.4 Apps small: getChats returns an UNTYPED http.get (no generic).
  7.5 Matching (no mismatch): generation request shape (workspaceId, documentIds,
       model, options, count, difficulty, types), chat CreateChat/Mentor/Concept,
       search query params (q, workspace_id, limit, kinds), citation objects,
       upload response (document + storage_path) all line up with the backend.
  7.6 Conflict of "needs edit/flag": review needs-edit & flag.

===============================================================================
8. BACKEND BUG FOUND (blocks frontend integration of 2 review actions)
===============================================================================
  * backend/review/service.py action_map references ReviewAction.NEEDS_EDIT and
    ReviewAction.FLAG, BUT the ReviewAction enum (src/validation/review_schema.py)
    only defines APPROVE / EDIT / REJECT / COMMENT.
  * => POST /review/needs-edit and POST /review/flag will raise AttributeError
    (500). Any frontend integration of those two review actions is blocked
    until the backend fixes this.

13. RECOMMENDED IMPROVEMENTS (priority-ordered)
===============================================================================
HIGH (blocking a real integration):
  R1 Decide ONE identity+storage strategy, then rewire the api/service layer:
       (a) Fully FastAPI — route auth/workspace/document through paths+http,
           authenticate locally with the backend.
       (b) Fully Supabase — implement backend Supabase JWT verification in
           deps.get_current_user, keep Supabase for workspaces/docs/storage, and
           let FastAPI generation/chat/review/search consume Supabase data.
2. Wire real "approve/reject/needs-edit/flag" calls via ReviewService and stand
      up an ExportService + export route that uses /exports; remove toast stubs.
3. Align contract types to Pydantic (review status/actions & "edited"; study-plan
     days; revision weakTopics) and stop auto-augmenting via inline lambdas.
4. Bind admin/analytics/pipeline stat cards to real data (remove hard-fixed
     numbers).
5. Add 401-refresh + 409/429 backoff in http.ts per BACKEND_CONTRACT.

MEDIUM:
  M1. De-duplicate toError/newId; delete the dead modules (§10).
  M2. Don't call non-existent /catalogue,/analytics,/models,/history endpoints;
        gate them until the backend implements them.
  M3. Add a route-level "requiresAuth" guard in __root (today only RoleGate).
  M4. Enforce max_upload_bytes client-side in UploadService (match the 413).
  M5. Migrate review/chat/history/notes writes from WorkspaceContext to
      service mutations.
  M6. Add a smoke test harness + a CI job that runs with VITE_ENABLE_MOCK=false
      against a test backend so split-brain wiring regresses loudly.

LOW:
 7. Delete dead modules, fix sitemap BASE_URL and coverage, centralise IDs,
    keep anon keys out of committed .env.local.

15. FINAL VERDICT
===============================================================================
A high-fidelity, mock-first prototype with a genuinely strong architecture and
clean code, but it is not wired end-to-end to the Phase 8 backend and is not
production-ready as a live real-mode product. The pivotal decision is choosing
ONE identity/storage stratum (R1) and wiring the missing App + Export +
persistence flow. The existing codebase is clean enough to absorb that work;
the remaining integration effort is well-scoped.
