PHASE 8 IMPLEMENTATION PLAN
===========================
Integration of the ai-content-agents backend repository with the Sensei AI
frontend.

Status: PLANNED (no code written). This document is the single roadmap for
Phase 8. It is written against:
  - PHASE8_BACKEND_ANALYSIS-from-backend.txt   (backend capability audit)
  - docs/FASTAPI_INTEGRATION.md                (frontend API contract)
  - docs/BACKEND_CONTRACT.md                   (frontend action -> endpoint map)
  - docs/DATABASE_SCHEMA.md                    (Supabase/Postgres schema)
  - docs/FRONTEND_ARCHITECTURE.md              (frontend layering)
  - docs/DEVELOPMENT_GUIDE.md, docs/SUPABASE_INTEGRATION.md
  - AGENTS.md (engineering principles that MUST hold after integration)

Terminology used below:
  - "backend repo" = ai-content-agents (Python; has src/, data/, scripts/,
    tests/, no HTTP API yet).
  - "frontend repo" = this repository (Sensei, TanStack Start + React 19).
  - "the API" = the new FastAPI service built in the backend repo.
  - "the store" = the backend's SQLite + Chroma persistence.
  - "Supabase" = the frontend's identity + database + storage + realtime.

================================================================================
0. EXECUTIVE SUMMARY
================================================================================
Phase 8 adds a FastAPI HTTP layer to the ai-content-agents backend repo and
point the Sensei frontend at it. The frontend already contains the complete
client contract (docs/FASTAPI_INTEGRATION.md), a single HTTP client
(src/api/http.ts), and a full mock layer, so the UI needs no restructuring:
Phase 8 is (a) build the API, (b) map every documented endpoint to an existing
backend component through a thin service facade, (c) replace the remaining
direct-Supabase branches in the frontend api modules with http.ts calls, and
(d) flip VITE_ENABLE_MOCK=false against the running API.

The review/export gate stays authoritative on the server. Supabase remains the
identity provider and the relational persistence layer; the backend's SQLite +
Chroma stores hold the AI-side artifacts (raw text, chunks, embeddings, the
review PlatformStore). The backend verifies the Supabase JWT on every request.

================================================================================
1. OVERALL ARCHITECTURE AFTER INTEGRATION
================================================================================
1.1 Topology

  Browser (Sensei SPA, SSR via TanStack Start)
    -> src/routes/* + src/components/*          UI only
    -> src/contexts (Auth/Workspace/Notification)
    -> src/services/* (business logic, Result<T>, never throws)
    -> src/api/*.api.ts (one file per domain)   ONLY layer that talks to network
    -> src/api/http.ts  (single HTTP client, single bearer-token holder)
    -> HTTPS / JSON / Bearer <Supabase JWT>
  FastAPI (backend repo, `uvicorn backend.main:app`, mounted at /api/v1)
    -> backend/routers/*        thin resource endpoints, authz, error mapping
    -> src/services/api_facade* thin facades (API -> service -> agent, never
                                 API -> agent directly)
    -> src/ingestion|retrieval|agents|study|validation|exports  (reused as a
       library, NO changes to core)
    -> Supabase (service-role): profiles, user_roles, workspaces, documents,
       generations, reviews, chats, chat_messages, notifications, history,
       analytics, storage (documents bucket)
    -> local stores: ingestion.db (SQLite), .chroma (Chroma vector index)
    -> LiteLLM (OpenAI-compatible gateway) -> external LLMs (server-side keys)

1.2 What stays where (data ownership)

  Owned by Supabase (written by the API via service-role):
    - profiles, user_roles (identity + roles)
    - workspaces (id/owner/name/subject/description/accent)
    - documents METADATA row (id, workspace_id, title, kind, size_bytes,
      pages, chunk_count, status, storage_path, notes, topics)
    - generations (id, kind, model, title, payload jsonb, document_ids,
      grounding_score, quality_score, review_status)
    - reviews + audit (append-only)
    - chats + chat_messages (with citations jsonb)
    - notifications (user/workspace/roles/kind/read)
    - history (id, workspace_id, kind, title, model, review_status)
    - analytics snapshots (rolled-up from the above)

  Owned by the backend store (SQLite ingestion.db + .chroma):
    - parsed/cleaned text, chunks, embeddings (Chroma "content_chunks")
    - PlatformStore rows: AgentRun, GeneratedOutput, Review, SystemEvent
    - the authoritative human-review lifecycle and export gate
    - learner-progress / revision spacing state (new table, see 13)

  The `documents` metadata row (Supabase) references chunks/embeddings that
  physically live in the backend store; chunk_count/status on the Supabase row
  are updated by the API after each ingest stage completes.

1.3 Layering rule (from the backend analysis, MUST be preserved)
  API routers never import src/agents/* or src/retrieval/* directly. They call
  src/services facades (new api_facade modules) following the existing
  MentorConceptService pattern. This keeps the core swappable and testable.

1.4 Frontend layering rule (from AGENTS.md, MUST be preserved)
  UI never imports src/api or src/mock. Services are the only place backend
  behaviour changes. Role checks go through useAuth().can()/RoleGate. All
  network flows through src/api/http.ts.

2. COMMUNICATION BETWEEN REPOSITORIES
================================================================================
2.1 Recommended model: two repos, HTTP contract only
  - Keep the frontend repo and the backend repo separate.
  - The backend repo OWNS the FastAPI service and runs it as a long-lived
    process (`uvicorn backend.main:app --host 0.0.0.0 --port 8000`).
  - The frontend repo OWNS the Vite dev server and the built SPA. It never
    imports Python; the backend never imports TS. The only interface is the
    JSON API documented in docs/FASTAPI_INTEGRATION.md + docs/BACKEND_CONTRACT.md.
  - Local dev: two processes.
      terminal 1 (backend repo):  uvicorn backend.main:app --reload
      terminal 2 (frontend repo): npm run dev   (VITE_API_BASE_URL set, see 18)
  - Production: containerise the backend (Dockerfile), expose HTTPS, CORS-allow
    the frontend origin. Frontend is served statically/edge.

2.2 Alternative (documented, not recommended for Phase 8)
  Monorepo copy or git submodule of the backend under `backend/` in this repo.
  Rejected because: the backend has its own test suite, CI and history; copying
  it into the frontend repo makes both heavier and breaks the backend repo's
  scripts/ and tests/conftest.py paths. Revisit only if a shared CI pipeline is
  required.

2.3 Contract governance
  - docs/FASTAPI_INTEGRATION.md + docs/BACKEND_CONTRACT.md are the SINGLE
    source of truth for paths, payloads and error envelopes.
  - Rule from BACKEND_CONTRACT.md: adding an endpoint means updating, in order:
    1. docs/BACKEND_CONTRACT.md + docs/FASTAPI_INTEGRATION.md
    2. src/types/api/*.contracts.ts
    3. the matching src/api/*.api.ts function
    4. its service
  - Add a contract test on BOTH sides (pytest asserting the JSON shapes in
    docs, and a frontend tsc typecheck on src/types/api) so the two repos can
    drift without breaking.

2.4 Versioning / URL prefix
  - The API is mounted under /api/v1 in FastAPI (single `APIRouter(prefix=...)`
    or root_path). The frontend sets VITE_API_BASE_URL=http://localhost:8000/api/v1
    so src/api/http.ts keeps its documented relative paths untouched
    (/generate/questions, /mentor/chat, /review/approve, ...). isMockMode()
    returns false because API_BASE_URL !== "/api".
  - /health is exposed at the root path too (unauthenticated) so load balancers
    can probe it.

3. FASTAPI ENDPOINTS TO CONSUME
================================================================================
3.1 Routing decision
  The frontend already calls, via src/api/*.api.ts, exactly these paths (the
  api modules put the path in `http.get/post/patch/delete`, http.ts prefixes
  env.API_BASE_URL). The API MUST implement these path names verbatim:

3.2 Endpoint inventory (frontend contract) -> backend implementation

  Auth (Supabase-backed; the API proxies/serves for completeness; frontend
  AuthService keeps using the Supabase JS client - see 17)
    POST /auth/login            -> Supabase signInWithPassword; returns session
    POST /auth/logout           -> Supabase signOut; 204
    GET  /auth/me               -> user + roles; 401 if token invalid
    POST /auth/refresh          -> exchange refresh_token; new session

  Workspaces (r/w Supabase `workspaces` + `workspace_with_owner` view)
    GET  /workspaces                            -> { workspaces: [...] }
    GET  /workspaces/{id}                       -> { workspace, data }
    POST /workspaces                            -> { workspace }
    PATCH /workspaces/{id}                      -> 204
    (NEW, recommended) GET /workspaces/bootstrap
        -> { workspaces, store } so the frontend bootstrap call is one request
        (today the frontend assembles this client-side; a dedicated endpoint
        removes a fan-out. Optional but recommended.)

  Documents + upload pipeline
    POST /upload (multipart: workspace_id, file)
        -> { document, storage_path }           frontend still uploads bytes to
           Supabase Storage (RLS-scoped) and then calls parse/chunk/embed; the
           API version of /upload can accept the file and write it to storage
           itself. RECOMMENDED: keep the frontend's storage upload (Phase 7
           behaviour, RLS intact) and make /upload an ingest trigger that
           reads the file back from storage via service-role.
    POST /documents/{id}/parse  -> { documentId, pages, text_length }
    POST /documents/{id}/chunk  -> { documentId, chunks: [...] }
    POST /documents/{id}/embed  -> { documentId, embedded, model }
    GET  /documents?workspace_id=               -> { documents: [...] }
    GET  /documents/{id}/chunks                 -> { chunks: [...] }
    PATCH /documents/{id}/notes                 -> 204
    DELETE /documents/{id}                      -> 204 (also drop chunks from
           the backend store + Chroma and the storage object)

  Generation
    POST /generate/questions    -> { generationId, kind, questions, grounding_score, quality_score }
    POST /generate/test-help    -> same shape (options.durationMinutes)
    POST /generate/flashcards   -> { generationId, kind, flashcards }
    POST /generate/study-plan   -> { generationId, kind, summary, sections, days }
    POST /generate/revision     -> { generationId, kind, summary, sections, weakTopics }
    Request body everywhere: { workspaceId, documentIds, model, options } +
    per-kind fields (count, difficulty, types, days, hoursPerDay, topics...).

  Chat
    POST /chats                 -> { chatId }
    GET  /chats?workspace_id=   -> { chats: [...] }
    POST /mentor/chat           -> { message, citations }
    POST /concept/chat          -> { message, citations }

  Review (authoritative server-side gate)
    GET  /review?workspace_id=  -> { itemIds }
    POST /review/approve | /review/reject | /review/needs-edit | /review/flag
         | /review/comment
        body { workspaceId, itemId, comment?, label? } -> { itemId, status, audit }
    GET  /review/audit?workspace_id= -> { audit: [...] }

  History & analytics
    GET  /history?workspace_id= -> { history: [...] }
    POST /history               -> row
    GET  /analytics?workspace_id=&range=30d
        -> { bloomDistribution, typeDistribution, activitySeries, topicCoverage }

  Catalogue, search, models, notifications
    GET  /models                -> { models: [...] }   (server-side catalogue)
    GET  /agents, /agents/{slug}
    GET  /pipeline/steps, /pipeline/stages
    GET  /catalogue             -> { documents, history, flashcards }
    GET  /search?q=&workspace_id=&kinds=&limit= -> { results, total }
    GET  /notifications?role=   -> { notifications, unread }
    PATCH /notifications/{id}/read
    POST /notifications/read-all

3.3 New capability endpoints (from PHASE8_BACKEND_ANALYSIS section 19) that the
    frontend does not call today but Phase 8 should add and the studio/pipeline
    pages can adopt:
    GET  /health                -> { status: "ok", version }
    POST /retrieval             { document_id, query, top_k } -> GroundedContext
    POST /exports               { output_id, format }         -> file/URL (gated)
    GET  /exports?workspace_id= -> approved-export records
    GET  /runs?workspace_id=    -> AgentRun/audit status for the pipeline page
    GET  /runs/{id}             -> run detail (grounding/support validation report)
    GET  /progress?workspace_id= and PATCH /progress  (see 13)

3.4 Response shape rule
  http.ts auto-unwraps `{ data: T }` when present and otherwise returns the
  payload verbatim. The contract docs show BARE payloads (e.g.
  `{ "workspaces": [...] }`). RECOMMENDATION: return the documented bare
  payloads exactly (single source of truth = docs), not a `data` envelope.
  Errors ALWAYS use `{ "error": { "code", "message", "details" } }` (rule 2 of
  BACKEND_CONTRACT.md).

4. RAG DOCUMENT INGESTION WORKFLOW
================================================================================
4.1 Flow (backend pipeline, exposed through the document endpoints)
  Upload (frontend -> Supabase Storage, RLS) 
    -> POST /upload records the Supabase documents row (status='uploaded')
    -> POST /documents/{id}/parse: API reads bytes from Supabase Storage
       (service role), calls ContentLoader.load_file/load_bytes:
       parser (txt/pdf/docx/md) -> cleaner -> quality gate -> (OCR fallback
       via loader._recover_scanned_pdf) -> returns page count + text length.
       Status row -> 'parsing'.
    -> POST /documents/{id}/chunk: TextChunker.chunk(text, document_id):
       paragraph -> sentence -> word -> character descent; chunk_size=2000,
       overlap=200 (RetrievalConfig); chunk ids "{document_id}-c{ordinal:04d}".
       Chunks persisted to SQLiteStore + response maps WsChunk shape
       ({ id, page, tokens, text, tags, section }).
    -> POST /documents/{id}/embed: index_chunks(index, document_id, chunks)
       via ChunkIndex.add_document -> HashingEmbeddingFunction (ONNX) ->
       Chroma collection "content_chunks" under CHROMA_DIR. Response
       { documentId, embedded, model } (model = embedder label from env).
       Status row -> 'indexed'. chunk_count updated.
  Dedup: SHA-256 of cleaned content (src/ingestion/dedupe.py) -> on hit, skip
  re-chunk/embed and reuse existing ids (surface a `duplicate` note).
  Failure at ANY stage: status row -> 'failed', error code `document_processing_failed`,
  detail { stage }. Frontend UploadService already treats parse/chunk/embed as
  best-effort (a failure never loses the persisted upload) - preserve that.

4.2 Request/response adapters
  - ParseResponse: { documentId, pages, text_length }
  - ChunkDocumentResponse: { documentId, chunks: WsChunk[] } - map backend
    chunk {id, text, page(ordinal->page heuristic), token_count} to WsChunk
    {id, page, tokens, text, tags, section} (tags/section default []/"").
  - EmbedDocumentResponse: { documentId, embedded: n, model }.

4.3 Concurrency
  SQLite is single-file and shared; ingestion of large files is the slowest
  path (embedding ~97% of ingest time). Phase 8 keeps ingest synchronous for
  correctness but MUST:
    - serialize per-document ingest with a per-workspace lock or a job table
    - return 409 `document_busy` if the same document is mid-ingest
    - cap upload size (413) and supported extensions (422)
  A full async job queue is listed as a Phase 8+ follow-up (see 21).

5. EMBEDDING WORKFLOW
================================================================================
5.1 Default path (reuse verbatim)
  - RETRIEVAL_EMBEDDER=onnx in backend .env.
  - HashingEmbeddingFunction (src/retrieval/index.py): deterministic ONNX
    hashing embeddings, batch limit ~5461.
  - CachingEmbeddingFunction (src/retrieval/performance.py): SHA-256 LRU cache
    -> repeated documents cost nothing.
  - Chroma client persists to CHROMA_DIR; collection "content_chunks".
5.2 Invariants
  - The index is coupled to the embedder: changing RETRIEVAL_EMBEDDER forces a
    FULL re-ingest. The API exposes this constraint (document status/version
    tag on the index; a /health or /pipeline/stages entry showing the active
    embedder so ops know when a re-ingest is owed).
  - Tests pin CHROMA_DIR and RETRIEVAL_EMBEDDER (tests/conftest.py) - new API
    tests MUST reuse those fixtures (isolated temp dirs) or the suite slows/
    fails offline.
  - The /documents/{id}/embed response model string is derived from the active
    embedder config, NOT hardcoded.
5.3 Optional (Phase 8 stretch, do not block core)
  - A provider-configurable embedding endpoint (OpenAI-compatible) behind the
    same embedder abstraction, controlled by RETRIEVAL_EMBEDDER; document that
    switching it invalidates the index.

6. RETRIEVAL WORKFLOW
================================================================================
6.1 Backend path (reuse verbatim)
  - POST /retrieval { document_id, query, top_k? } and every generation/chat
    endpoint internally:
      ChromaRetriever.retrieve(query, scope=RetrievalScope(document_id))
        -> top-k (default top_k=5, min_score=0.0), score = 1 - distance,
           ordered (-score, ordinal, chunk_id), STRICTLY document-scoped.
  - GroundedContext built by build_grounded_context(query, chunks) ->
    { chunks, chunk_ids, is_sufficient }; as_prompt_content() assembles the
    prompt text. InsufficientGroundingError -> API 422
    `insufficient_grounding` { message, details: { retrieved, required } }.
6.2 Workspace-scoped retrieval for chat/generation
  - The frontend always sends workspaceId + documentIds[]. The API resolves
    the documentIds to the caller's workspace (membership check), then queries
    per document; cross-document leakage is impossible because retrieval is
    document-scoped (backend invariant).
  - When documentIds is empty (chat with no selection), the API falls back to
    the workspace's indexed documents (max N, configurable) OR returns a
    clearly-marked ungrounded response - NEVER silently whole-document prompts
    (the 1.7M-token wall from the backend analysis).
6.3 Citations mapping (frontend)
  - RetrievedChunk -> Citation { doc: documentId, page, chunk, snippet, score }.
  - verify_references(output.references, context) and validate_support(...)
    run AFTER generation; failures are recorded on the GeneratedOutput
    validation_report and surface in the review UI, they do NOT auto-reject.

================================================================================
7. CONTEXT ASSEMBLY
================================================================================
7.1 Assembly order per generation request
  1. Resolve scope: workspace membership + documentIds -> document ids.
  2. Per document: build queries from the request (user_question/topic/
     difficulty + extracted allow-list topics).
  3. Retrieve top-k per document (section 6), dedupe chunks.
  4. build_grounded_context -> GroundedContext (is_sufficient must be true).
  5. as_prompt_content() -> the grounded passage text that fills {content} in
     the YAML prompt template.
  6. Reference/support verification uses the SAME GroundedContext (single
     source of evidence for a run).
7.2 Context fidelity rules
  - The prompt tells the model "Use ONLY the uploaded educational content" and
    "will be reviewed by a human" (baked into templates - do not edit).
  - Study-lane agents inject the deterministic topic allow-list
    (extract_topics) into the prompt; invented topics are rejected by
    grounding errors before/without an LLM call.
  - Grounding scores exposed to the frontend are computed from the same
    validation pipeline the review page already keys on (grounding >= 98,
    quality >= 8.5 auto-flag thresholds live in ReviewService).

8. PROMPT GENERATION
================================================================================
8.1 Templates (no changes to core)
  - Platform agents: src/prompts/{mentor,concept,question_bank,test_help}.yaml
    with name/description/role/instructions/output_schema/notes/prompt_template.
    Filled at runtime with .format({content}, {user_question}, {difficulty}).
  - Study agents: src/study/prompts/{flashcards,study_plan,revision}_prompt.yaml
    with the allow-list injected.
8.2 API responsibility for prompts
  - The API must not build prompts itself; it only passes request fields that
    the templates expect. Unknown fields -> 422 validation.
  - `model` from the frontend maps server-side to an LLM config (LiteLLM model
    alias) - the prompt text is model-independent.
  - difficulty strings: the frontend sends "Beginner|Intermediate|Advanced";
    the backend DifficultyLevel enum uses lowercase variants - normalize in
    the facade (case-fold to backend enum) and map back on output.
8.3 JSON discipline
  - Agents return JSON only (json.loads -> Pydantic model_validate). Malformed
    or schema-invalid output -> 500 `agent_output_invalid` with
    validation_report in details; never pass raw LLM text to the client.

9. MENTOR AGENT INTEGRATION
================================================================================
9.1 Endpoint mapping
  - POST /mentor/chat { workspaceId, chatId, message, model, documentIds }.
  - Backend: MentorAgent.generate(content=<grounded context prompt>,
    user_question=message, difficulty, context=GroundedContext). NOT the legacy
    src/generation MockGenerator (dual-stack hazard - see 21).
9.2 Conversation state
  - The backend agent is single-shot. Chat state lives in Supabase
    chat_messages (roles user/assistant). The API service reads the last K
    messages (default 12) for the chatId, prepends them to the prompt as prior
    context, stores the new user turn, and stores the assistant reply + cited
    chunk metadata (citations jsonb). Truncation budget ~4000 tokens of history.
9.3 Response mapping
  - MentorOutput { explanation, key_points, next_steps, references } ->
    frontend { message: { id, role: "assistant", text, time }, citations }.
    text = explanation (+ key points/next steps formatted); citations from
    context chunks that verify_references accepted.
9.4 Review wiring
  - Wrap via ValidatorBase.build_generated_output -> GeneratedOutput(status=
    PENDING) persisted to PlatformStore. The mentor reply itself returns to the
    chat immediately, but an exportable artifact is only produced after review.
9.5 Agent catalogue entry (GET /agents/mentor)
  - Serve the metadata the /agents page already renders (name, tagline,
    bullets, icon, runs count from PlatformStore RUN_* events).

11. WORKSPACE INTEGRATION
================================================================================
11.1 Read path
  - GET /workspaces serves Supabase `workspace_with_owner` (owner, counts,
    pending_review_count, review_status) - the exact shape workspace.api.ts
    maps today (mapWorkspace). Move the mapping server-side (FastAPI returns

  - GET /workspaces/bootstrap (recommended new endpoint) returns workspaces +

11.2 Write path
  - POST /workspaces -> insert (owner_id from JWT user), 409 on duplicate slug.
  - PATCH /workspaces/{id} -> owner/admin only (403 otherwise).
11.3 Authorization model (server-side, mirrors ROLE_PERMISSIONS)
  - membership: the JWT user must own the workspace OR be a member (Phase 7
    rules). Reviewer/admin roles act across owned/assigned workspaces per the

11.4 Realtime
  - The WorkspaceContext listens to Supabase postgres_changes on `workspaces`.
    Because the API writes workspaces THROUGH Supabase (service role), those
    realtime events still fire and the existing subscription keeps working -
    no frontend change needed. Keep this property; do not introduce a second
    data path for workspaces.

12. DOCUMENT LIBRARY INTEGRATION
================================================================================
12.1 The library page (/library) reads useWorkspace().data.docs, which today
     is seeded by getWorkspaceBootstrap() and mutated by addDoc/updateDoc/
     removeDoc. After Phase 8 all of these flow through http.ts:
  - list: GET /documents?workspace_id= -> WsDoc[] (metadata from Supabase
    documents, kind/size/pages/status/tags/notes + chunk_count)
  - notes: PATCH /documents/{id}/notes
  - delete: DELETE /documents/{id} -> API drops storage object + chunks +
    Chroma entries + document row; frontend removeDoc stays as-is (optimistic
    local + API call).
  - upload: UploadService.ingest keeps its stage callback; the stages now
    correspond to real HTTP calls: upload (storage) -> store (row) ->
    parse/chunk/embed (API). The persisted document's `status` reflects the
    latest completed stage, so the library shows Processing -> Ready accurately.
12.2 Chunks viewer
  - GET /documents/{id}/chunks serves backend SQLite chunks mapped to WsChunk.
    Page/section/tags are best-effort (ordinal heuristic) until the backend
    chunker exposes them.
12.3 Notes (text documents)
  - A "Note" kind document is created via createDocument (row only); its body
    is stored in the notes field and may be ingested on demand by calling
    parse with the note text (API enhancement, optional in Phase 8).

13. PROGRESS TRACKING INTEGRATION
================================================================================
13.1 What exists
  - Backend: revision spacing is deterministic (easy=+7d/medium=+3d/hard=+1d)
    and NOT persisted; no learner-progress model.
  - Frontend: analytics (activitySeries, topicCoverage), weakTopics in
    /generate/revision, and per-run history rows.
13.2 What Phase 8 adds
  - A `progress` store in the backend (new SQLite table `progress`, or a
    Supabase `progress` table - RECOMMENDED: Supabase table + RLS, so analytics
    and realtime work without a second sync path).
    Columns: workspace_id, user_id, topic, strength (0-100), last_seen,
    due_revision (date), attempts, correct, source (review/quiz/export).
  - Endpoints:
      GET  /progress?workspace_id=  -> { topics: [{ topic, strength, due, source }] }
      PATCH /progress { workspaceId, topic, delta, correct, attempts }
    (upsert, scoped + role-checked).
  - The RevisionAgent's spacing offsets are written back on "hard/medium/easy"
    review events so revision sheets are personalised (weakTopics derived from
    strength, not static).
13.3 Feed into /generate/revision
  - weakTopics in the response come from the progress store (low strength,
    due soon), falling back to "No signal yet" when empty - matching the mock
    behaviour the UI already renders.
13.4 Pipeline/ingestion progress
  - /runs exposes per-run status (PENDING/RUNNING/SUCCEEDED/FAILED) with stage
    detail so the pipeline page telemetry and any progress bars are truthful.

14. REVIEW WORKFLOW
================================================================================
14.1 Authority
  - The review/export gate is NEVER modified (backend section 15): OutputStatus
    lifecycle PENDING -> EDITED -> APPROVED (REJECT keeps PENDING),
    assert_exportable(). All review actions go through ReviewService/
    PlatformStore on the API; the frontend's review page calls ReviewService
    (which already calls /review/*) - the local WorkspaceContext.setReview
    mutation remains as optimistic UI but the server response is authoritative.
14.2 Endpoint semantics
  - GET /review?workspace_id= -> itemIds of GeneratedOutputs with
    status=PENDING for the workspace (reviewer/admin only, 403 otherwise).
  - POST /review/approve|reject|needs-edit|flag|comment -> ReviewService action
    -> PlatformStore review row + SystemEvent REVIEW_ACTION -> ALSO insert into
    Supabase `reviews` (append-only audit for realtime/analytics) and the
    Supabase `generations` row's review_status. Response { itemId, status,
    audit } exactly per contract.
  - GET /review/audit?workspace_id= -> platform history (REVIEW_ACTION events)
    merged with Supabase reviews, newest first.
14.3 Auto-flag
  - On generation, if grounding < 98 or quality < 8.5 (ReviewService thresholds)
    the API calls the flag action with actor "System" - mirroring
    shouldAutoFlag() so both sides agree.
14.4 Export gate
  - /exports only lists/serves APPROVED outputs; assert_exportable() before any
    JSON/CSV/Markdown/PDF render (src/exports/export.py). Export of an
    unapproved output -> 403 `not_exportable`.

16. ERROR HANDLING
================================================================================
16.1 Envelope (MANDATORY, matches BACKEND_CONTRACT rule 2 + http.ts):
  { "error": { "code": "<snake_case>", "message": "human text", "details": {...} } }
16.2 Code map (keep in sync with src/lib/result.ts ERROR_CODES + the docs):
  400 validation_error          invalid body/query
  401 unauthorized               missing/expired/invalid token
  403 forbidden                  role/workspace not permitted
  404 not_found                  unknown id
  409 conflict                   duplicate workspace slug, document busy
  413 payload_too_large          upload too big
  422 validation_error           schema failure OR unsupported file OR
                                 insufficient_grounding (details: stage/retrieved)
  429 rate_limited               model or endpoint rate limit
  500 unknown_error              provider failure
  500 agent_output_invalid       schema-invalid LLM output (details: report)
  500 document_processing_failed stage + reason
  403 not_exportable             export gate blocked
16.3 Implementation
  - FastAPI exception handlers (fastapi.exceptions.RequestValidationError,
    Starlette HTTPException, and custom AppError base) -> envelope. A catch-all
    500 logger with request id.
  - backend/errors.py defines AppError(code, message, details, status) and a
    handler that maps Python exceptions from the libraries (GroundingError,
    InsufficientGroundingError, ValidationError, ExportError) to codes.
16.4 Frontend behaviour (unchanged)
  - http.ts raises HttpError(status, message, body); result.ts attempt() turns
    it into Result<T> with the body.code; pages render via useNotify/AsyncSection.
  - Network timeout: http.ts has no timeout today - add AbortController timeout
    (~90s default, models can take up to 60s) so a hung backend returns
    network_error instead of hanging the UI.

17. AUTHENTICATION FLOW
================================================================================
17.1 Identity stays with Supabase Auth (frontend)
  - AuthService/AuthContext keep using the Supabase JS client: signInWithPassword,
    signOut, refresh, persistSession, onAuthStateChange. When a session is
    created/refreshed, AuthService already calls setAccessToken() which feeds

17.2 Backend verification (every request)
  - Dependency get_current_user: parse `Authorization: Bearer <token>`,
    verify the Supabase JWT. RECOMMENDED: verify signature + exp + aud/iss
    locally with pyjwt using the Supabase JWT secret (fast, no network); then
    load roles from `user_roles` (service role) OR decode app_metadata claims.
    Fallback for HS-alg flexibility: supabase.auth.getUser(token) via admin
    client (network, slower - use only when local verify fails).

    require_workspace_owner - every protected router dependency-injects them.

17.4 /auth/* endpoints

    credentials/refresh_token through Supabase Auth (admin) and return the
    contract Session shape.

    The anon key + JWT secret live server-side. CORS only allows configured

21. RISKS (and mitigations)
================================================================================
  R1  Embedder coupling: switching RETRIEVAL_EMBEDDER invalidates .chroma.
      -> Keep embedder pinned in prod config; expose embedder in /health and
         /pipeline/stages; run re-ingest as a documented ops task.
  R2  SQLite single-file concurrency under API traffic.
      -> Per-document lock + 409 document_busy + a job table for ingest; defer
         Postgres/pgvector migration to a later phase. Cap concurrent LLM runs.
  R3  Circular import src.validation <-> src.retrieval (lazy PEP-562).
      -> API imports respect the lazy-import pattern in
         src/validation/__init__.py; never import src.validation eagerly from
         src.retrieval (and vice versa) in the new facades.
  R4  Path/shape drift between repos.
      -> Contract tests both sides; response mappers centralized in
         backend/schemas.py; add an endpoint to BACKEND_CONTRACT.md only with
         its frontend contract updated first.
  R5  GeneratedQuestion vs backend model mismatch.
      -> QuestionBankOutput fields differ from the frontend GeneratedQuestion
         (bloom, estMinutes, quality, grounded, review, citations). The facade
         must compute/synthesize these (bloom via evaluation heuristics,
         quality = validation score, grounded = verification score, review =
         PENDING, estMinutes from type). Validate with contract tests.
  R6  Dual generation stacks (legacy src/generation MockGenerator still imported
      by src/app.py).
      -> The API only ever calls src/agents/* and src/study/*; add a test that
         fails if a facade imports src.generation.
  R7  Review-gate bypass risk: any path that exports/approves outside
      ReviewService/assert_exportable.
      -> No direct store writes from routers; code-review checklist + a test
         asserting /exports rejects PENDING outputs.
  R8  Whole-document prompt wall (1.7M-token ceiling).
      -> No "analyze whole document" endpoint in Phase 8; retrieval-scoped only.
  R9  Supabase JWT verification fragility (algorithm/issuer).
      -> Verify with pyjwt (HS256) + fallback to admin getUser(); keep the
         authn dependency abstracted so a switch is one file.
  R10 Realtime dependence on Supabase for workspace/review/notification events.
      -> The API writes those tables via service role, so existing Supabase
         realtime subscriptions keep firing; do NOT bypass Supabase for these
         tables.
  R11 Everything lands PENDING -> nothing exportable without a human.
      -> Intentional (product rule). Provide a safe, explicit admin-only
         auto-approve switch in the API config ONLY if required, clearly logged.
  R12 CI slowness from real embedding code.
      -> New API tests reuse conftest.py pinned CHROMA_DIR/RETRIEVAL_EMBEDDER
         and temp dirs; keep live LLM tests gated by RUN_LIVE_TESTS.
  R13 Stale backend docs (MOCK_MODE/OpenRouter) must not be implemented from.
      -> Build from PHASE8_BACKEND_ANALYSIS sections 14-16 + source code, not
         docs/ mentor-concept-lane-week3.md.
  R14 Auth state between Supabase client and http.ts.
      -> Single token holder already exists (setAccessToken); add a guard that
         http.ts never sends a token to a different origin than VITE_API_BASE_URL.
